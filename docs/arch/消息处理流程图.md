## 4. 过滤器链处理流程

```mermaid

    FilterMgr --> CreateCtx[创建 FilterContext]
    CreateCtx --> GetFilters[获取已注册过滤器列表<br/>按优先级排序]
    
    GetFilters --> CheckEmpty{过滤器列表为空?}
    CheckEmpty -->|是| AcceptDefault[默认接受消息]
    CheckEmpty -->|否| LoopStart[开始遍历过滤器]
    
    LoopStart --> NextFilter{还有过滤器?}
    NextFilter -->|否| AcceptAll[所有过滤器都接受]
    NextFilter -->|是| CheckEnabled{过滤器启用?}
    
    CheckEnabled -->|否| SkipFilter[跳过此过滤器]
    CheckEnabled -->|是| ExecuteFilter[执行过滤器]
    
    ExecuteFilter --> RecordTime[记录执行时间]
    RecordTime --> FilterLogic{过滤器逻辑}
    
    FilterLogic -->|DuplicateMessageFilter| CheckDB[检查数据库是否存在]
    FilterLogic -->|EmptyMessageFilter| CheckContent[检查内容是否为空]
    FilterLogic -->|CustomFilter| CustomLogic[自定义逻辑]
    
    CheckDB --> DBResult{消息已存在?}
    DBResult -->|是| Reject1[返回 REJECT]
    DBResult -->|否| Accept1[返回 ACCEPT]
    
    CheckContent --> ContentResult{内容为空?}
    ContentResult -->|是| Reject2[返回 REJECT]
    ContentResult -->|否| Accept2[返回 ACCEPT]
    
    CustomLogic --> CustomResult{自定义判断}
    CustomResult -->|拒绝| Reject3[返回 REJECT]
    CustomResult -->|接受| Accept3[返回 ACCEPT]
    
    Reject1 --> RecordReject[记录拒绝统计]
    Reject2 --> RecordReject
    Reject3 --> RecordReject
    
    RecordReject --> LogReject[记录拒绝日志<br/>包含原因]

    AcceptAll --> ReturnTrue
    
    ReturnTrue --> ProcessMsg[继续处理消息<br/>保存+解析+插件]
    ReturnFalse --> DiscardMsg[丢弃消息<br/>不保存，不处理]
```

### 过滤器优先级

过滤器按优先级从高到低执行：

1. **ChannelMonitoringFilter (10)** - 频道监控（最高优先级）
2. **MessageTypeFilter (90)** - 类型过滤（可选）
3. **DuplicateMessageFilter (95)** - 检查重复消息
4. **EmptyMessageFilter (100)** - 检查空消息
5. **自定义过滤器 (0-89)** - 用户自定义

### 过滤器特点

- **快速失败**: 任何过滤器返回 REJECT，立即停止链并丢弃消息
- **错误容错**: 过滤器出错时默认接受消息（fail-open）
- **统计记录**: 记录每个过滤器的执行时间和拒绝次数
- **动态管理**: 支持运行时启用/禁用过滤器

## 5. 频道监控动态更新流程

### 5.1 概述

`ChannelMonitoringFilter` 支持通过 REST API 动态增删改监控频道列表，无需重启应用。使用 Spring 事件机制实现解耦，确保线程安全。

### 5.2 动态更新流程图

```mermaid
sequenceDiagram
    participant Client as REST 客户端
    participant Controller as ChannelController
    participant Service as ChannelService
    participant EventPub as ApplicationEventPublisher
    participant Filter as ChannelMonitoringFilter
    participant DB as MongoDB
    participant Cache as 内存缓存

    Note over Client,Cache: 场景1: 创建监控频道
    Client->>Controller: POST /api/channel<br/>{channelId, monitoringStatus: true}
    Controller->>Service: create(dto)
    Service->>DB: save(channel)
    DB-->>Service: 保存成功
    Service->>EventPub: publishEvent(CHANNEL_ADDED)
    Service-->>Controller: 返回 ChannelVO
    Controller-->>Client: 200 OK
    
    EventPub->>Filter: @EventListener<br/>handleChannelMonitoringEvent
    Filter->>Cache: monitoringChannels.add(channelId)
    Filter->>Filter: log.info("频道已添加到监控列表")
    
    Note over Client,Cache: 场景2: 更新监控状态
    Client->>Controller: PUT /api/channel/{id}<br/>{monitoringStatus: false}
    Controller->>Service: update(id, dto)
    Service->>DB: 查询并更新
    DB-->>Service: 更新成功
    Service->>Service: 检测监控状态变化
    Service->>EventPub: publishEvent(CHANNEL_UPDATED)
    Service-->>Controller: 返回 ChannelVO
    Controller-->>Client: 200 OK
    
    EventPub->>Filter: @EventListener<br/>handleChannelMonitoringEvent
    Filter->>Cache: monitoringChannels.remove(channelId)
    Filter->>Filter: log.info("频道已停用监控")
    
    Note over Client,Cache: 场景3: 删除频道
    Client->>Controller: DELETE /api/channel/{id}
    Controller->>Service: deleteById(id)
    Service->>DB: 查询 channelId
    DB-->>Service: 返回 channelId
    Service->>DB: deleteById(id)
    DB-->>Service: 删除成功
    Service->>EventPub: publishEvent(CHANNEL_REMOVED)
    Service-->>Controller: 成功
    Controller-->>Client: 200 OK
    
    EventPub->>Filter: @EventListener<br/>handleChannelMonitoringEvent
    Filter->>Cache: monitoringChannels.remove(channelId)
    Filter->>Filter: log.info("频道已从监控列表移除")
```

### 5.4 并发安全保证

```mermaid
flowchart TD
    Start([多个并发请求]) --> Concurrent[并发 API 调用]
    
    Concurrent --> API1[API 请求 1<br/>创建频道 A]
    Concurrent --> API2[API 请求 2<br/>更新频道 B]
    Concurrent --> API3[API 请求 3<br/>删除频道 C]
    
    API1 --> Service1[@Transactional<br/>数据库操作]
    API2 --> Service2[@Transactional<br/>数据库操作]
    API3 --> Service3[@Transactional<br/>数据库操作]
    
    Service1 --> Event1[发布事件 1]
    Service2 --> Event2[发布事件 2]
    Service3 --> Event3[发布事件 3]
    
    Event1 --> Async1[异步事件处理]
    Event2 --> Async2[异步事件处理]
    Event3 --> Async3[异步事件处理]
    
    Async1 --> Filter1[Filter.handleEvent]
    Async2 --> Filter2[Filter.handleEvent]
    Async3 --> Filter3[Filter.handleEvent]
    
    Filter1 --> Cache[ConcurrentHashMap<br/>线程安全缓存]
    Filter2 --> Cache
    Filter3 --> Cache
    
    Cache --> Operation1[add/remove 操作]
    Operation1 --> End([所有操作完成])
    
    style Start fill:#e1f5ff
    style Concurrent fill:#fff4e1
    style Service1 fill:#4caf50,color:#fff
    style Service2 fill:#4caf50,color:#fff
    style Service3 fill:#4caf50,color:#fff
    style Cache fill:#2196f3,color:#fff
    style End fill:#e1f5ff
```

**线程安全机制**：

1. **ConcurrentHashMap.newKeySet()**
   - 线程安全的 Set 实现
   - 支持并发读写
   - 无需额外同步

2. **volatile 标志**
   - `volatile boolean initialized` 保证可见性
   - 防止指令重排序

3. **双重检查锁定（DCL）**
   - 延迟初始化时使用
   - 避免重复加载

4. **事件异步处理**
   - 不阻塞 API 调用
   - 事件处理失败不影响数据库操作

### 5.5 性能特性

| 特性 | 说明 | 性能 |
|------|------|------|
| 缓存查找 | O(1) 时间复杂度 | < 1μs |
| 事件发布 | 异步非阻塞 | < 1ms |
| 事件处理 | 后台线程执行 | 不影响 API 响应 |
| 内存占用 | 每个频道 8 字节（Long） | 1000 频道 ≈ 8KB |
| 延迟初始化 | 首次使用时加载 | 避免启动时查询 |

### 5.6 使用示例

```bash
# 1. 创建监控频道
curl -X POST http://localhost:8080/api/channel \
  -H "Content-Type: application/json" \
  -d '{
    "channelId": -1001234567890,
    "channelUsername": "tech_news",
    "channelTitle": "科技新闻",
    "monitoringStatus": true
  }'
# → 过滤器自动添加到缓存，立即生效

# 2. 停用监控

  -H "Content-Type: application/json" \
  -d '{"monitoringStatus": false}'
# → 过滤器自动从缓存移除，立即生效

# 3. 删除频道
curl -X DELETE http://localhost:8080/api/channel/{id}
# → 过滤器自动从缓存移除，立即生效
```

## 9. 媒体组状态机（并发安全优化）

### 9.1 概述

为了解决媒体组处理中的并发竞态条件，系统引入了状态机机制来管理媒体组的生命周期。状态机配合分段锁（Striped Lock）确保并发安全。

### 9.2 状态转换图

```mermaid
stateDiagram-v2
    [*] --> COLLECTING: 首次接收消息
    COLLECTING --> PROCESSING: 超时（2秒无新消息）
    PROCESSING --> COMPLETED: 处理成功
    PROCESSING --> COLLECTING: 处理失败（允许重试）
    COMPLETED --> [*]: 清理状态
    
    note right of COLLECTING
        状态：收集中
        行为：接受新消息
        锁保护：是
    end note
    
    note right of PROCESSING
        状态：处理中
        行为：拒绝新消息
        锁保护：是
    end note
    
    note right of COMPLETED
        状态：已完成
        行为：拒绝新消息
        锁保护：否
    end note
```

### 9.3 并发安全的媒体组处理流程

```mermaid
sequenceDiagram

    end
    
    Note over Msg,DB: 场景3：并发冲突（新消息 vs 定时任务）

    Msg->>State: 检查状态
    State-->>Msg: PROCESSING
    Msg->>Msg: 拒绝消息（状态不允许）
    Msg->>Lock: 释放锁
```

## 媒体组（消息组）处理说明

### 什么是媒体组？

媒体组（Media Album）是 Telegram 中将多个媒体文件（图片、视频、文档、音频）作为一组发送的功能。在 TDLib 中，属于同一媒体组的消息具有相同的非零 `mediaAlbumId`。

### 处理机制

1. **缓冲机制**：
   - 收到带有 `mediaAlbumId` 的消息时，不立即处理
   - 将消息添加到缓冲区，等待同组的其他消息
   - 使用 `chatId:mediaAlbumId` 作为缓冲区的键

2. **超时机制**：
   - 每秒检查一次缓冲区
   - 如果某个媒体组 2 秒内没有新消息，认为该组已完整
   - 触发批量处理

3. **批量处理**：
   - 按消息 ID 排序，确保顺序一致
   - 检查媒体组是否已存在（去重）
   - 为每条消息设置媒体组信息
   - 批量保存到数据库
   - 统一输出到控制台

### 数据结构

```java
// ChannelMessage 实体
private Long mediaAlbumId;              // 媒体组ID，0表示不属于任何组
private Boolean isMediaGroup;           // 是否为媒体组消息
private Integer mediaGroupItemCount;    // 媒体组中的项目数量
private List<Long> mediaGroupMessageIds; // 媒体组中所有消息的ID列表
```

## 15. 并发安全性说明

### 15.1 并发场景

系统需要处理以下并发场景：

1. **多频道并发**：不同频道的消息同时到达
2. **单频道并发**：同一频道的多条消息同时到达
3. **重复推送**：同一消息被 Telegram 重复推送
4. **媒体组并发**：媒体组的多条消息几乎同时到达

### 15.2 线程安全组件

#### ChannelMonitoringFilter
```java
// ✅ 线程安全
private final Set<Long> monitoringChannels = ConcurrentHashMap.newKeySet();
private volatile boolean initialized = false;

// 使用双重检查锁定（DCL）
if (!initialized) {
    synchronized (this) {
        if (!initialized) {
            loadMonitoringChannels();
            initialized = true;
        }
    }
}
```

**安全性保证**：
- `ConcurrentHashMap.newKeySet()` 保证并发读写安全
- `volatile` 保证可见性
- DCL 保证只初始化一次

#### DuplicateMessageFilter
```java
// ✅ 基本安全，但有优化空间
private final Set<String> processingMessages = ConcurrentHashMap.newKeySet();

// 两层检查机制
1. 内存缓存：快速检查正在处理的消息
2. 数据库查询：检查已保存的消息
```

**安全性保证**：
- 内存缓存防止并发重复
- 数据库唯一索引防止持久化重复

**已知问题**：
- 缓存清理时机可能导致额外的数据库查询
- 详见并发安全性优化设计文档

#### 媒体组处理
```java
// ⚠️ 存在并发问题
private final Map<String, List<TdApi.Message>> mediaGroupBuffer = new ConcurrentHashMap<>();
private final Map<String, Long> mediaGroupTimestamps = new ConcurrentHashMap<>();
```

**已知问题**：
- 定时任务和新消息处理之间存在竞态条件
- 可能导致消息丢失或媒体组拆分
- **严重程度**：高
- **修复方案**：见深度分析文档

### 15.3 数据一致性保证

#### 数据库层面
```javascript
// MongoDB 唯一索引
db.raw_messages.createIndex({chatId: 1, messageId: 1}, {unique: true})
db.raw_messages.createIndex({chatId: 1, mediaAlbumId: 1}, {unique: true})
```

**保证**：
- 单文档操作是原子的
- 唯一索引防止重复插入
- 即使并发插入，MongoDB 会拒绝重复

#### 应用层面

**过滤器链执行**：
```
消息 → 过滤器1 → 过滤器2 → ... → 保存 → 插件处理
```

**特点**：
- 串行执行，不是原子操作
- 每个消息使用独立的 FilterContext
- 过滤器之间不共享状态

**风险**：
- 过滤器通过但保存失败：消息会重试
- 保存成功但插件失败：消息已持久化但未处理

### 15.4 性能考虑

#### 过滤器优先级设计
```
ChannelMonitoringFilter (10) → 内存查找，极快
MessageTypeFilter (90) → 简单判断，很快
DuplicateMessageFilter (95) → 数据库查询，较慢
EmptyMessageFilter (100) → 字符串检查，很快
```

**原则**：
- 快速检查放在前面
- 耗时检查放在后面
- 尽早拒绝不需要的消息

#### 并发处理能力

**当前设计**：
- TDLib 使用内部线程池
- 消息处理是同步的
- 不同频道的消息可以并发处理

**瓶颈**：
1. 数据库连接池大小
2. 过滤器链串行执行
3. 媒体组缓冲区锁竞争

**优化建议**：
- 增加数据库连接池
- 使用消息队列解耦
- 实现分段锁减少竞争

### 15.5 故障恢复

#### 消息丢失场景

**场景1：应用崩溃**
- Telegram 会重新推送未确认的消息
- 过滤器会检测重复并拒绝
- 结果：不会丢失

**场景2：数据库故障**
- 保存失败，从缓存移除
- Telegram 重新推送
- 过滤器允许通过
- 结果：会重试

**场景3：媒体组处理中断**
- 部分消息已保存
- 重启后，新消息会被拒绝（重复）
- 结果：可能不完整 ⚠️

#### 重复处理场景

**场景1：Telegram 重复推送**
- 过滤器检测重复
- 拒绝处理
- 结果：不会重复

**场景2：并发处理**
- 内存缓存防止并发
- 数据库索引防止重复保存
- 结果：基本不会重复

**场景3：缓存清理后重试**
- 可能通过过滤器
- 数据库索引会拒绝
- 结果：不会重复保存，但会多次尝试

## 过滤器链说明

### 什么是过滤器链？

过滤器链是在消息保存到数据库和交给插件处理之前执行的一系列过滤器。被过滤器拒绝的消息将被丢弃，不会保存到数据库，也不会交给插件处理。

### 为什么需要过滤器链？

1. **避免重复处理**: DuplicateMessageFilter 检查消息是否已存在，避免重复保存和处理
2. **节省存储空间**: 过滤掉无效消息（如空消息），减少数据库存储
3. **提高处理效率**: 尽早过滤掉不需要的消息，减少后续处理开销
4. **灵活的过滤规则**: 支持自定义过滤器，满足不同的业务需求

### 内置过滤器

#### 1. DuplicateMessageFilter (优先级: 95)

**功能**: 避免插件重复处理已经保存过的消息

**检查逻辑**:
- 单条消息: 使用 `chatId + messageId` 检查数据库
- 媒体组消息: 使用 `chatId + mediaAlbumId` 检查数据库

**拒绝原因示例**:
```
Duplicate message: chatId=-1001234567890, messageId=123456
Duplicate media group: chatId=-1001234567890, mediaAlbumId=789012
```

#### 2. EmptyMessageFilter (优先级: 100)

**功能**: 过滤空消息

**检查逻辑**:
- 拒绝 content 为 null 的消息
- 拒绝文本内容为空或只有空格的文本消息
- 非文本消息不检查（如图片、视频等）

**拒绝原因示例**:
```
Message content is null
Text message is empty
```

### 过滤器执行流程

```
消息接收
    ↓
过滤器链（按优先级执行）
    ↓
EmptyMessageFilter (100) → 检查空消息
    ↓
DuplicateMessageFilter (95) → 检查重复
    ↓
其他过滤器 (0-94) → 自定义逻辑
    ↓
所有过滤器都接受？
    ↓ 是
保存到数据库 → 解析消息 → 插件处理
    ↓ 否
丢弃消息（不保存，不处理）
```

### 过滤器特性

1. **优先级控制**: 数值越大优先级越高，越早执行
2. **快速失败**: 任何过滤器返回 REJECT，立即停止并丢弃消息
3. **错误容错**: 过滤器出错时默认接受消息（fail-open策略）
4. **统计记录**: 记录每个过滤器的执行时间和拒绝次数
5. **动态管理**: 支持运行时启用/禁用过滤器
6. **自动注册**: Spring Bean 自动发现和注册

### 创建自定义过滤器

```java
@Component
public class MyCustomFilter extends AbstractMessageFilter {
    
    @Override
    public String getName() {
        return "MyCustomFilter";
    }
    
    @Override
    public int getPriority() {
        return 50;  // 中等优先级
    }
    
    @Override
    protected FilterResult doFilter(TdApi.Message message, FilterContext context) {
        // 你的过滤逻辑
        if (shouldReject(message)) {
            context.setRejectReason("拒绝原因");
            return FilterResult.REJECT;
        }
        return FilterResult.ACCEPT;
    }
```


### 16.5 媒体组原子性保证

```mermaid
sequenceDiagram
    participant Scheduler as ForwardScheduler
    participant Queue as QueueManager
    participant Batch as 批次累加器
    participant TDLib as TelegramClient

    Scheduler->>Queue: getPendingItems(batchSize)
    Queue-->>Scheduler: [Item1, Item2, Item3, ...]

        Scheduler->>Scheduler: 检查频率限制
        alt 频率限制
            Scheduler->>Scheduler: 跳出循环
        else 未限制
            Scheduler->>Scheduler: count = getMessageCount(item)
            
            alt totalCount + count > 100
                Note over Scheduler: 加上当前项会超过限制
                Scheduler->>Scheduler: 检查 batch 是否为空
                
                alt batch 不为空
                    Scheduler->>TDLib: forwardBatch(batch)

                    Note over Scheduler: 单项超过100条（异常情况）

                end
            end
            
            Scheduler->>Batch: batch.add(item)
            Scheduler->>Batch: totalCount += count
        end
    end
    
    alt batch 不为空
        Scheduler->>TDLib: forwardBatch(batch)
    end
    
    Note over Scheduler,TDLib: 关键：媒体组不会被截断<br/>整个媒体组要么在当前批次<br/>要么在下一批次
```

### 16.9 关键特性

1. **媒体组原子性**：
   - 媒体组作为一个整体处理，不会被拆分
   - 如果批量转发时加上媒体组会超过100条限制，整个媒体组移到下一批次
   - 媒体组的所有消息ID按递增顺序排序（TDLib要求）

2. **批量转发优化**：
   - 将多个队列项合并到一个TDLib API调用中
   - 减少API调用次数，提高转发效率
   - 遵守TDLib单次转发100条消息的限制

3. **频率限制**：
   - 使用Resilience4j RateLimiter控制转发速率
   - 避免触发Telegram的速率限制
   - 被限流的消息保持PENDING状态，下次重试

4. **重试机制**：
   - 转发失败自动重试，最多3次
   - 达到最大重试次数后标记为FAILED
   - 记录详细的错误信息便于排查

5. **错误处理**：
   - 使用whenCompleteAsync避免阻塞TDLib响应线程
   - 捕获所有异常，不影响其他插件
   - 提供详细的错误日志和建议
